# Shared CLI Session, Review, Settings, and Diff Design

## Summary

Codex Web will use a shared Codex app-server daemon on macOS so a CLI task can remain live while the browser resumes it, receives the same events, and continues the conversation. The same release will expose native Codex permission profiles and model reasoning effort, add inline review of uncommitted changes, preserve complete multi-file diffs, and refine the existing three-column interface.

The first release deliberately supports live handoff between Codex CLI and Codex Web on macOS. Codex Desktop tasks remain readable as durable history but are not advertised as live or directly controllable. Windows retains the existing embedded app-server behavior because Codex 0.147 daemon lifecycle management is Unix-only.

## Goals

- Let Codex Web discover, resume, observe, interrupt, approve, and continue a task running through the same macOS Codex daemon as the CLI.
- Preserve task continuity when either the CLI or Web disconnects.
- Let users select an allowed Codex permission profile and a reasoning effort supported by the selected model.
- Let users start an inline review of uncommitted changes from the loaded task.
- Render complete, structured, multi-file diffs without losing the original unified diff.
- Polish the existing three-column interface without replacing its core navigation model.
- Preserve the browser-facing protocol boundary: browsers never receive raw app-server messages or local socket paths.

## Non-goals

- Live takeover of a task owned by the local Codex Desktop app.
- Migrating an already-running embedded CLI task into the daemon.
- Windows daemon lifecycle management or live CLI handoff.
- Review targets for a base branch, commit, or custom instructions.
- Detached review threads.
- Editing `~/.codex/config.toml` or another global Codex configuration file.
- Replacing the existing Cloudflare Access remote-authentication model.

## Compatibility Baseline

The design targets the protocol generated by `codex-cli 0.147.0` with `codex app-server generate-ts --experimental`. Required native methods and notifications are:

- `thread/list`, `thread/resume`, `thread/turns/list`, and `thread/loaded/list`
- `thread/settings/update` and `thread/settings/updated`
- `permissionProfile/list`
- `review/start`
- `turn/diff/updated`
- the existing turn, item, approval, and token-usage messages

Codex Web continues using tolerant decoders. If a required method or field is absent, only the affected feature becomes unavailable and the service exposes a bounded compatibility diagnostic.

## Architecture

### macOS shared-daemon mode

At service startup, Codex Web resolves the configured Codex executable and invokes the idempotent `codex app-server daemon start` lifecycle command. It parses the single JSON response, validates that the returned socket path is absolute and points under the active Codex home, and connects to that owner-only Unix socket using the app-server WebSocket transport.

The connection performs the normal JSON-RPC `initialize` request and `initialized` notification. The existing `JsonRpcPeer` remains the request-correlation and notification abstraction, but it consumes a transport-neutral message stream rather than assuming newline-delimited stdio. A new Unix-socket WebSocket transport owns the HTTP upgrade, frame encoding and decoding, ping/pong, close behavior, payload bounds, and backpressure. A maintained WebSocket implementation that accepts a custom Unix `net.Socket` connection is preferred over a handwritten frame parser.

Codex Web does not stop the daemon during normal shutdown. This lets the CLI continue an active task after the browser or Web service exits. Unexpected transport closure moves the service into reconnecting state, rejects in-flight Web requests, reconnects to the daemon with bounded backoff, and restores the currently loaded thread subscription before normal browser traffic resumes.

When a compatible default daemon socket already exists, a normally launched CLI automatically reuses it. Therefore Codex Web must be started before the CLI task, or the user must start the daemon first. An embedded CLI that was already running cannot be migrated; the UI explains this limitation rather than claiming the task is live.

### Embedded fallback mode

Windows continues to spawn `codex app-server` over stdio. macOS falls back to the same embedded mode if daemon lifecycle setup or Unix-socket connection fails. Existing history, new-task, turn, attachment, and approval workflows remain available. The service snapshot reports a bounded handoff capability state so the UI can say that live CLI takeover is unavailable without treating the whole service as unusable.

### Connection ownership

The server has one app-server connection and continues multiplexing normalized state to authenticated browser WebSockets. Browser reconnection remains sequence-based. Raw native messages, native request IDs, daemon paths, and configuration contents never cross the browser protocol.

## Thread Discovery and Handoff

The server refreshes the first page of `thread/list` after app-server connection, after reconnect, and on a modest interval while at least one browser is connected. Refresh is also triggered when the browser regains focus. The interval is a catalog refresh, not turn-event polling; a resumed task streams its work normally.

`ThreadSummary` adds normalized fields for native source, native status, and direct-input capability when known. The UI treats a task as live only after `thread/resume` succeeds and the native response says that direct input is accepted. A source string or durable status alone is not sufficient evidence.

Selecting a task calls `thread/resume` with recent-turn pagination. When the task is already loaded in the shared daemon, resume rejoins it and subscribes this connection to its events. The adapter hydrates older turns through `thread/turns/list` as it does today, while bounding item count and bytes. The loaded response also supplies authoritative model, reasoning effort, approval policy, sandbox projection, and active permission profile.

On reconnect, the server reconnects to app-server first, resumes the previously loaded task, then publishes an authoritative browser snapshot. Events that occurred while the Web service was disconnected are reconstructed from the resumed thread history; the browser event buffer continues covering only browser-to-server connection gaps.

## Browser Protocol

The browser protocol version increments because snapshot and request shapes change.

### Catalog types

`ModelSummary` gains:

- `supportedReasoningEfforts: Array<{ id: string; description?: string }>`
- `defaultReasoningEffort?: string`

`PermissionProfileSummary` contains:

- `id: string`
- `description?: string`
- `allowed: boolean`

`ThreadSummary` gains:

- `source?: "cli" | "vscode" | "exec" | "appServer" | "subAgent" | "unknown"`
- normalized `status?: string`
- `canAcceptDirectInput?: boolean`

### Effective task settings

The snapshot adds an optional `threadSettings` object for the loaded task:

- `threadId`
- `model`
- `effort?: string`
- `permissionProfile?: { id: string; extends?: string }`
- normalized approval-policy and sandbox labels for display

Native `thread/settings/updated` notifications replace this object atomically. The client does not optimistically treat a selection as effective; it shows a pending state until the server publishes the effective settings. A rejected update restores the last authoritative value.

### Diff state

Each file-change item contains every native change rather than only `changes[0]`:

- `path`
- `kind`
- `diff`
- item status and truncation metadata

The snapshot also carries the latest bounded turn-level unified diff from `turn/diff/updated`, keyed by thread and turn. The original string is retained even when the client successfully parses it into files and hunks.

### Review state

The snapshot carries an optional inline review state with `threadId`, `turnId`, and `status`. Review output continues through ordinary visible items and final assistant messages.

### Browser methods

The protocol adds:

- `permissionProfile.list`
- `thread.settings.update`
- `review.start`

`thread.settings.update` accepts a loaded thread ID and either a permission-profile ID, an effort, or both. The gateway rejects empty updates and strings outside bounded limits. The adapter verifies that a selected permission profile appears in the current catalog and is allowed before forwarding it.

`review.start` accepts only a loaded thread ID. The adapter always sends target `{ type: "uncommittedChanges" }` and delivery `"inline"` in this release.

The first `turn.start` for a new task includes the selected permission-profile ID and reasoning effort so they become sticky native thread settings. Later changes use `thread/settings/update`.

## Permission and Reasoning Controls

Permission profiles come from `permissionProfile/list`; Codex Web does not hard-code sandbox combinations. Disallowed profiles remain visible but disabled with their native description. The active profile comes from `activePermissionProfile` in start/resume/settings responses.

Reasoning choices come from the selected model's `supportedReasoningEfforts`. Changing models selects the persisted effort only if the new model supports it; otherwise it selects that model's native default. Custom future effort strings remain representable because the native protocol models effort as an open string.

For an existing loaded task, a control change calls `thread/settings/update`. If a turn is running, the UI labels the selection as applying to the next turn. For a new-task draft, selections stay local until the first turn starts. Successful selections are saved in Codex Web's non-secret settings and become defaults for the next new task. No global Codex config is modified.

## Review and Diff Behavior

“Review changes” is enabled only for a loaded, idle, directly controllable task with no review already running. It starts an inline review of uncommitted changes. Native entered/exited-review items appear as concise activity states, and the final review message remains in the conversation.

The Changes tab combines the latest turn-level unified diff with complete file-change items. It shows:

- an ordered file list with add, modify, delete, or rename state when available
- additions and deletions derived from parsed hunks
- a selected-file unified diff with line numbers and addition/deletion/context styling
- running, completed, failed, empty, truncated, and parse-error states

The parser is presentation-only. A parse failure displays the original bounded unified diff in a plain preformatted fallback. This avoids data loss when a newer Codex version emits an unfamiliar patch shape.

## Interface Design

The selected layout keeps the current three columns.

### Left sidebar

Tasks are grouped into Running and Recent sections. A live shared-daemon task displays a compact `LIVE · CLI` state. Stored tasks and tasks that cannot accept direct input are never styled as live. Search covers title, preview, directory, source, and status.

### Workspace header

The header shows task title and connection state, followed by compact controls for permission profile and model/reasoning effort. “Review changes” is the primary task action. Controls use native labels and tooltips, expose disabled reasons, and remain keyboard accessible.

### Conversation and composer

Conversation remains the main surface. Command, file-change, plan, review, and connection events use consistent expandable activity rows. The composer retains attachment, directory, and model controls; effort moves next to the model and permissions remain visible in the task header so the effective execution boundary is always apparent.

### Right inspector

The inspector has Activity and Changes tabs. Activity contains approvals, commands, status, and token use. Changes contains the file list and structured diff. Tab labels show pending approval or changed-file counts without relying on color alone.

### Responsive behavior

At tablet widths the inspector becomes an overlay/drawer opened by the existing mobile navigation. At phone widths tasks, conversation, activity, and changes are mutually exclusive views using the existing bottom navigation pattern. Controls wrap without horizontal scrolling, and the diff view may scroll horizontally inside its code region only.

## State Races and Error Handling

- If another client resolves an approval first, Codex Web consumes `serverRequest/resolved`, removes the card, and treats a later `alreadyResolved` response as a benign race.
- If another client changes thread settings, `thread/settings/updated` replaces the displayed settings.
- If another client starts a turn, native turn events update the loaded task and disable Review until the turn finishes.
- If resume reports that direct input is unavailable, history remains visible while composer, interrupt, settings, and Review actions are disabled.
- If daemon startup fails on macOS, the service records a diagnostic, starts embedded mode, and exposes `liveHandoff: "unavailable"` with a safe reason.
- If the shared daemon version is incompatible, affected capabilities are disabled independently. Basic history and conversation remain available when their methods still work.
- Socket and native payloads keep existing byte, item-count, approval-count, and diagnostic bounds.

## Security

- Validate lifecycle JSON before trusting the daemon socket path.
- Connect only to an absolute local Unix socket resolved for the active Codex home; never accept a browser-provided socket path.
- Rely on Codex's owner-only socket permissions and do not proxy that socket directly to HTTP or browser WebSocket clients.
- Keep permission profile IDs and descriptions bounded; never expose the underlying full permission policy unless the normalized Web UI needs it.
- Continue authenticating every HTTP and browser WebSocket request before state or actions are exposed.
- Keep approval decisions atomic and audit only bounded normalized fields.

## Testing Strategy

### Transport and lifecycle

- Unit-test daemon lifecycle JSON parsing, idempotent start, invalid socket paths, incompatible versions, and embedded fallback.
- Test Unix-socket WebSocket initialization, text messages, ping/pong, close, malformed frames, payload bounds, backpressure, and reconnect.
- Test that normal Web shutdown leaves the daemon running.

### Adapter and state

- Test thread catalog refresh and source/status normalization.
- Test resuming an already-loaded task and reconstructing history after reconnect.
- Test permission-profile decoding and rejection of disallowed selections.
- Test model effort catalogs, defaults, model changes, and settings notifications.
- Test inline uncommitted review request parameters and review state transitions.
- Test all file changes in an item plus turn-level diff updates and truncation.

### Client

- Test Running and Recent grouping and strict live-status rules.
- Test settings pending, success, rejection, and cross-client update behavior.
- Test Review button enablement and duplicate-start prevention.
- Test diff parsing for add, modify, delete, rename, multiple hunks, missing newline markers, malformed input, and fallback rendering.
- Test keyboard navigation and narrow-screen inspector behavior.

### End to end

- Extend fake Codex to expose permission profiles, effort metadata, settings updates, review events, and multi-file diffs.
- Exercise task resume, live event streaming, settings changes, approval resolution, Review, and diff selection in Playwright.
- Provide an opt-in macOS native smoke test using an isolated Codex home and two app-server clients. It verifies that both observe the same thread and that disconnecting one client does not terminate the turn or daemon.

## Rollout and Documentation

- Document that macOS users must start Codex Web or the daemon before launching a CLI task intended for handoff.
- Document that CLI launch overrides that prevent implicit daemon reuse also prevent live handoff.
- Label Desktop tasks as history-only in this release.
- Document Windows as embedded mode with no live CLI handoff.
- Keep the embedded mode available as a compatibility fallback until shared-daemon support is stable.
